The Turbodev Shopify WhatsApp Integration connects your Shopify store to WhatsApp via webhook events. Each time Shopify fires a webhook (e.g. a new order, a payment, a shipment update), Turbodev receives the payload, optionally enriches it with additional Shopify API data, and then sends a pre-configured WhatsApp template message to the customer.

This guide documents every available variable for all 9 supported webhook workflows so that you can confidently map data to your WhatsApp message templates without guesswork.

## How Variable Mapping Works

When you design a WhatsApp template in Turbodev, each {{variable}} placeholder in the template body must be mapped to a field path. There are two kinds of fields: 

•    Regular fields - come directly from the raw Shopify webhook payload. They are always available immediately when the webhook fires and cost no extra API calls.

•    Computed fields - enriched by the Turbodev backend. The system makes an additional Shopify API call or performs a calculation to produce these. They are NOT present in the raw webhook body. Crucially, computed fields are only fetched when you actually map them in your template - they are never fetched unnecessarily.

•    Array fields (\[\]) - when a field is an array (e.g. line\_items), Turbodev returns the first element by default unless otherwise noted.

**integration.brandName** - this is the store brand name you configured in the Integration Settings panel inside Turbodev. It is always available in every workflow.

</Tip>

 

## fulfillment\_status is Always Null on New Orders

<Warning>
  When a new order is created (orders/create) or payment is captured (orders/paid), the fulfillment\_status field is ALWAYS null or empty. Shopify does not populate it until fulfillment actually begins. Never use body.fulfillment\_status as a condition or variable on these two triggers it will always be blank.
</Warning>

 

## How Routing Works for fulfillments/update

Workflows 5, 6, and 7 (Partially Fulfilled, Out for Delivery, and Delivered) all listen to the same Shopify fulfillments/update webhook. Shopify sends every fulfillment event to a single endpoint - it cannot split them by shipment status.

The Turbodev backend solves this automatically. Each workflow is tagged with a triggerType:

•    order\_partially\_fulfilled\_with\_tracking - fires when some items are fulfilled and shipment\_status is NOT out\_for\_delivery or delivered.

•    out\_for\_delivery - fires only when shipment\_status = out\_for\_delivery.

•    order\_delivered - fires only when shipment\_status = delivered.

 

For every incoming fulfillments/update event, the backend inspects the payload and routes it to exactly the matching workflow. The other two workflows are silently ignored. You do not need to add any conditional logic in your templates.

<Note>
   For Workflows 5, 6, and 7, all customer and order data (name, phone, address, order total, product list) is NOT in the fulfillments/update webhook payload. Turbodev fetches it automatically from the parent order using the body.order\_id before sending the message.
</Note>

WhatsApp template URL buttons work by combining a fixed prefix (configured in the template) with a dynamic suffix variable. For example, your template button might have a fixed prefix of:

https://yourstore.myshopify.com

And the variable fills in the path portion:

/checkouts/abc123/recover

<Info>
  **URL Button Rule:** If your template has a URL button with a fixed domain prefix, map body.abandoned\_checkout\_url\_path to the button variable NOT body.abandoned\_checkout\_url. Using the full URL in the button variable will break the link because the domain would appear twice. For plain text in the message body, use body.abandoned\_checkout\_url (the full URL).
</Info>

# Common Mistakes

The following mistakes appear frequently when configuring workflows. Each one will result in blank variables, broken links, or messages sending to the wrong customers.

### **Mistake 1 - Using fulfillment\_status on orders/paid or orders/create**

**Problem:** body.fulfillment\_status is ALWAYS null when a new order is created or when payment is captured. Mapping this variable will produce an empty string in your WhatsApp message.

**Fix:** Do not use body.fulfillment\_status on Workflow 1 (orders/create) or Workflow 2 (orders/paid). It only becomes meaningful in the fulfillments/update workflows (5, 6, 7).

### **Mistake 2 - Using the full URL in WhatsApp URL button variables**

**Problem:** WhatsApp URL button templates have a fixed domain prefix defined in the template itself. If you also pass the full URL (including the domain) as the variable, the final URL will look like: https://yourstore.myshopify.comhttps://yourstore.myshopify.com/checkouts/... which is broken.

**Fix:** For URL button variables, always map body.abandoned\_checkout\_url\_path which contains only the path portion (e.g. /checkouts/abc123/recover). Reserve body.abandoned\_checkout\_url (the full URL) for plain text body variables only.

### **Mistake 3 - Using body.total\_price in Workflows 5, 6, or 7**

**Problem:** The fulfillments/update webhook payload does not include a reliable order total in body.total\_price. Mapping it will either be empty or show an incorrect value.

**Fix:** Always use body.order\_total\_price in Workflows 5, 6, and 7. This computed field is fetched from the parent order and accurately reflects the full order total.

### **Mistake 4 - Using body.cancelled\_at (ISO) instead of the formatted date**

**Problem:** body.cancelled\_at returns a raw ISO 8601 timestamp like 2026-06-04T10:30:00\+00:00 which is confusing and unprofessional in a customer-facing WhatsApp message.

**Fix:** Use body.cancelled\_at\_dd\_mm\_yyyy which returns a clean, readable date like 04/06/2026.

# How Routing Works

Shopify sends all fulfillment events to a single webhook endpoint. It cannot split events by shipment status. This means that every time a carrier updates a shipment - whether the status is 'confirmed', 'in\_transit', 'out\_for\_delivery', or 'delivered' - Shopify fires a fulfillments/update event.

Turbodev handles this automatically using a triggerType system. Here is how it works step by step:

•    Shopify fires a fulfillments/update event for any carrier status change.

•    Turbodev receives the event and reads the body.shipment\_status and body.fulfillment\_status fields.

•    The backend matches the event to the correct triggerType based on these rules:

◦    shipment\_status = out\_for\_delivery → routed to Workflow 6 (Out for Delivery)

◦    shipment\_status = delivered → routed to Workflow 7 (Order Delivered)

◦    fulfillment\_status = partial AND shipment\_status is neither of the above → routed to Workflow 5 (Partial Fulfillment)

•    The matched workflow's WhatsApp template is sent. All other workflows for this event are silently skipped.

<Info>
  **You do not need to add conditional logic:** As a Turbodev user, you simply configure each workflow (5, 6, 7) with its own WhatsApp template. The routing happens automatically in the backend. There is no risk of accidentally sending the 'out for delivery' message when an order is only partially shipped, or vice versa.
</Info>
